# Security and privacy review

Existing strengths: loopback-only desktop server, authenticated startup handshake, sessions/RBAC, store scope, encrypted backup test coverage, redacted diagnostics, event-ID/payload-collision rejection, ordered aggregate checks, fail-closed provider webhook verification, and owner-only device enrollment/registration/revocation endpoints.

V4 threats requiring implementation/testing: stolen device credential, forged payment/GSP webhook, vendor/store IDOR, aggregate-version tampering, stale quote, unsafe media, SSRF, catch-up-safe rate limiting, and PII exposure in exports/backups. Local event replay and payload collision controls are verified against the simulator; cloud-issued device credentials, signed transport, and cross-tenant authorization remain external-contract work.

The local privacy boundary now provides authenticated vendor-scoped export, correction requests, erasure requests, active-order and legal-hold rejection, PII scrubbing with accounting/operational references retained, address archiving, consent scrubbing, checksum-labelled exports, and audit events without writing customer PII into the audit payload. API and domain self-tests cover export, correction, erasure, request idempotency, store isolation, and unauthenticated access denial. Device enrollment is authenticated to `settings.manage`, returns private key material only as a one-time response, and keeps production `Registered` activation fail-closed until an external receipt exists. This is an operational control, not a legal certification: DPDP purpose/notice, retention, grievance, breach, controller/processor allocation, and marketplace deletion propagation remain **NEEDS_LEGAL_VALIDATION** and require the real control-plane contract.

The legacy local customer portal was also corrected: customer IDs are no longer bearer credentials and the route no longer reads the process-default tenant. An authenticated operator issues a short-lived HMAC token bound to the tenant, store and customer; the public read-only route validates signature, expiry and subject binding before entering the scoped store context. `test:customer-portal` covers token issuance, read-only invoice access, missing-token rejection, and the existing PWA assets. The token secret is required at runtime; no universal secret is embedded in the desktop binary. Marketplace customer access must still be implemented through the real cloud contract.
